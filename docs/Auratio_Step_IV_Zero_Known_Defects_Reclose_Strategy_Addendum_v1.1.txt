======================================================================
1. PURPOSE
======================================================================

This addendum governs the reopening, hardening, verification, and final re-closing of
Auratio Step IV — UI Coding after Android runtime testing exposed real interaction
defects that had not been detected by the previous visual and automated QA passes.

The purpose is NOT to redesign Auratio or expand MVP scope.

The purpose is to establish a stricter Step-IV completion standard so that Auratio moves
to Step V only after the complete frontend has:

- zero known functional defects,
- zero known navigation defects,
- zero known misleading/dead interactive controls,
- zero known material visual discrepancies,
- zero known role-boundary defects,
- clean automated test results,
- successful real runtime interaction QA,
- successful adversarial QA,
- successful final human acceptance testing.

No non-trivial software process can mathematically guarantee that absolutely no latent
bug exists. Therefore, the authoritative release criterion in this addendum is:

                         ZERO KNOWN DEFECTS

Step IV must not be described as complete or locked again until every gate in this
addendum has passed after the final Step-IV code change.

4. CORE PRINCIPLE — TEST BEHAVIOR, NOT ONLY SCREENS
======================================================================

The prior Step-IV process proved that:

- a screen can visually match Figma,
- source code can compile,
- automated tests can pass,
- route declarations can exist,

while a real user can still encounter controls that do nothing or behavior that violates
the specification.

Therefore, Step-IV re-close QA must validate BOTH:

A. Visual correctness
B. Runtime behavioral correctness

Visual QA alone is insufficient.
Widget/unit tests alone are insufficient.
Source-code review alone is insufficient.
Manual testing alone is insufficient.

The final Step-IV decision must be supported by multiple independent verification layers.


======================================================================
5. PHASE A — MOBILE REPAIR
======================================================================

Mobile repair shall be performed in controlled batches.

----------------------------------------------------------------------
5.1 REPAIR BATCH R1 — CORE INTERACTION INTEGRITY
----------------------------------------------------------------------

R1 covers only the confirmed high-priority mobile defects and their direct dependencies.

Required R1 scope:

1. Canonical mobile bottom navigation
   - Home
   - Tracks
   - Progress
   - Profile
   - Every non-current canonical destination must navigate correctly.

2. All 13 tracks
   - Every track must be browsable.
   - Every track must be selectable for evaluation.
   - Path selection must remain personalization only and must not restrict track access.

3. Reusable selected-track state
   - Avoid duplicating 13 Track Details screens.
   - Use one reusable local/mock track model/state.
   - Preserve exact user-facing track labels and durations.
   - Give tracks stable technical identifiers.

4. Active evaluation journey parameterization
   - Current selected track information must propagate through the applicable evaluation
     journey instead of remaining hard-coded to Business Pitch / Sales Pitch.
   - Historical/demo data must not be blindly rewritten.

5. Pending Moderation
   - Normal runtime must remain pending until an external/mock state change or explicit
     navigation occurs.
   - It must not auto-approve or auto-transition after a timer.

6. Rejected evaluation
   - “Start a New Evaluation” must be a real accessible interactive control.
   - It must release the user into the new-evaluation journey as defined by the approved
     frontend behavior.

7. Regression tests
   - Navigation regression coverage.
   - All 13 tracks accessible.
   - Selected-track consistency.
   - Pending Moderation does not auto-transition.
   - Rejected retry works.

8. Runtime QA
   - Actual Flutter runtime interaction testing.
   - Runtime visual captures for visually affected states.
   - Figma comparison where visuals changed.

R1 must be completed, reviewed, and approved before R2 begins.


----------------------------------------------------------------------
5.2 REPAIR BATCH R2 — RESIDUAL INTERACTION INTEGRITY
----------------------------------------------------------------------

R2 begins with an AUDIT before any implementation.

Required audit targets include, at minimum:

- Tracks category/filter controls
- Events Division filter
- Events Path filter
- Events Date filter
- Monthly leaderboard control
- AI/Human leaderboard switching
- Home CTAs
- Home active-evaluation entry
- Settings actions
- Sign Out behavior
- “How Ranking Works”
- all chips/tabs/buttons/links/cards that visually imply interactivity
- all remaining hard-coded current-evaluation assumptions
- Android Back behavior
- modal/dialog actions
- scrolling and keyboard interaction
- navigation edge cases

For each suspect control, determine whether it is:

A. intentionally presentation-only according to the authoritative product/prototype, or
B. expected to be interactive and therefore defective.

Only verified defects are repaired.

R2 must not introduce backend/database/API behavior. Step-IV behavior remains local/mock
where production services belong to later steps.

----------------------------------------------------------------------
7.2 INDEPENDENT REVIEW BEFORE FIXING
----------------------------------------------------------------------

Antigravity findings are not automatically accepted as product defects.

Each finding must be checked against:

- authoritative Auratio specifications,
- Figma,
- role semantics,
- frontend source code.

Only confirmed defects are authorized for repair.

This prevents accidental “fixes” to intentional presentation-only behavior or scope that
belongs to later database/backend/API work.


----------------------------------------------------------------------
7.3 CONTROLLED PORTAL REPAIR
----------------------------------------------------------------------

Confirmed portal defects shall be repaired in narrow batches.

Each batch must:

- have an explicit defect list,
- preserve approved visuals,
- avoid unrelated redesign,
- avoid Step V+ work,
- include appropriate tests,
- include browser/runtime evidence,
- end in a clean focused commit,
- receive review before the next batch begins.


----------------------------------------------------------------------
7.4 PLAYWRIGHT REGRESSION SUITE
----------------------------------------------------------------------

Critical portal journeys must receive repeatable browser regression coverage.

At minimum, cover representative flows for:

- Shared authentication
- Volunteer assignment/evaluation journey
- Admin Volunteer CRUD
- Admin assignment/reassignment
- Admin Event CRUD
- moderation workflow where represented in Step IV
- Super Admin Admin-account lifecycle
- protected Root Super Admin behavior
- Volunteer denied access to Admin routes
- Admin denied access to Super-Admin-only routes
- direct protected-route access
- important filters/tabs/dialogs that were repaired

Playwright tests must validate actual outcomes, not merely that elements exist.


======================================================================
8. PHASE D — ADVERSARIAL QA
======================================================================

Before Step IV can re-close, deliberately attempt to break the frontend.

Examples include:

- repeated rapid taps/clicks
- unusual Back navigation
- rapid primary-tab switching
- browser refresh mid-flow
- direct URL entry
- empty form submission
- invalid form values
- canceling dialogs
- reopening dialogs
- long-content scrolling
- keyboard opening/closing
- switching away mid-flow
- revisiting completed states
- attempting forbidden role routes
- small/large portal viewports
- horizontal-overflow scenarios
- repeated action submission where relevant
- stale mock-state transitions
- navigation after state mutation

Adversarial QA is not optional for the final Step-IV gate.

======================================================================

Step V — Database must NOT begin while this Step-IV re-close process is incomplete.
